## ② 问题台账

### P0-1 装入 1.4.1 后启动崩溃，整个 profile 插件全不加载

- **现象**：重启报 `startup failed: 1 required plugin did not activate`，失败项 `modules`，错误 `client-modules: dsh-theme-palette declares dsh.client but exports no "./client" bundle`；界面所有插件消失。
- **根因**：1.4.1 为补展示元数据加了 `exports`，只写了 `.`、`./locale/*.json`、`./icon`，**漏 `"./client"`**。`client-modules` 取不到就抛错，而 `modules` 是 required 插件 → 全量不加载。
- **处置**：1.4.2 补齐 8 个子路径；对 profile 内**全部 22 个**声明 `dsh.client` 的包做同类扫描（全部可解析）。
- **防复发**：`tools/release.mjs` 断言 `exports["./client"]` 存在且文件可读 → 见 `WORKFLOW-NOTES.md §2`。
- **教训**：官方 check 不校验这条，当时 12 项全绿。

### P0-2 profile 插件清单被写成 2 条（28 → 2）

- **现象**：`~/.dsh/profiles/desktop/package.json` 的 `dsh.profile.bundles` 只剩 `dsh-base` / `dsh-web-app`；包全在 node_modules。
- **根因（v2 修订：从"未定位"改为可验证假设）**：三种可能，按可能性排序——
  1. **失败恢复路径改写**：启动失败时宿主把 bundles 收敛为"能确认可用的"两条（与崩溃同一时间窗，最可能）；
  2. 我改 profile（重命名插件那步）时写坏了文件，但中间通过 `pnpm install` 与两次成功启动，排除；
  3. 外部工具（如 `dsh plugin` 类脚本）写入。
  **验证方法**：在 profile 目录留一份 `package.json` 的 sha256 快照脚本（每小时或启动前后各记一次），复发时看是哪一步写掉的；同时用 `git`/`fs.watch` 记录 mtime 变化时刻，与崩溃日志时间戳对齐。
- **处置**：从备份 `_backup/profile-package-2026-10-21.before-rename.json` 恢复 28 条并逐条核对可定位。
- **防复发**：改 profile 前必备份 + 改完核对 bundles 数量 → 见 `WORKFLOW-NOTES.md §3`。
- **教训**：用户看到"插件都没了"时，真实含义通常是**清单丢了**，不是包丢了。

### P1-1 其他插件是否"更好"：竞争位势（实测 2026-10-22）

| 插件 | ★ | 周下载 |
|---|---|---|
| dsh-claude-style | 272 | **6862** |
| catppuccin-theme | 67 | 1871 |
| dsh-ui-appearance | 23 | 1086 |
| dsh-theme-plugin | 4 | 143 |
| dsh-studio | 2 | 5 |
| **我们** | **0** | 暂无数据 |

- **他们更强**：覆盖能力（壁纸/玻璃/字体/18 套预设/图片取色/撤销重做）、可编辑性（三色 + 对比度 → 派生 70+ token）、可访问性专项（High Contrast）、manifest 的兼容性履历（`dsh.compatibility`，**宿主不读**，目录站展示）。
- **我们更强**：按角色在真实承载面上求解对比度（432 组合零违规）、配色轴与明暗轴正交、组件级 token 覆盖（标题/加粗/代码块/气泡/按钮/滚动条/开关/注释）、自愈、工程门禁 + 截图回归、五语文档 + 4 语设置页。
- **结论**：他们是"外观商店"，我们是"配色引擎"；用户量差距来自生态位与可编辑性，不来自技术深度。

### P2-1 文档承诺了跑不起来的回归层

- **现象**：`tools/README.md` 写桌面真机截图回归可用；实际 `shoot-desktop.mjs` 的 `ready` 必然失败。
- **根因**：脚本依赖 `window.__DSH_THEME_PALETTE_DEV__` 的 `attach`，**全仓无任何地方创建这个全局**（只在测试桩里定义）。
- **处置**：文档如实降级；**修复列在 A-5，未完成**。
- **教训**：写进文档 ≠ 存在 → `WORKFLOW-NOTES.md §8`。

### P2-2 我自己的两次判断错误

1. **semver 预发布误判**：用库默认语义算出"0.3.0-rc.1 会被拒"，准备发 1.4.4 去"修"；复核宿主源码发现带 `includePrerelease`，结论相反。已回滚并固化为脚本断言。
2. **目录收录误读**：`grep -c "dsh-theme-palette"` 得 2，误以为已收录；实际是另一个插件 `dsh-theme-palettes`（超串）。

### P2-3 交付形态不符合生态规范，事后补

五语 README、topic（`dsh-plugin` / `dsh-theme`）、展示元数据（`locale/*.json` + `./icon` 导出）、过期版本钉——都是**硬门槛**，应先查规范再动手 → `WORKFLOW-NOTES.md §6`。

## ⑤ 结论

- 这一轮把插件从"能跑"做到"有工程约束"：432 组合零违规、门禁 12/12、发版链有兼容性与导出预检、安全审计整改完毕。
- 代价是一次 P0（`exports`）与一次环境事故（清单塌缩），两者都**不是配色算法问题，而是"边界与装配"问题**——正是客户端插件最容易翻车的地方。
- 当前最大短板不是代码，而是**没有用户反馈、没有可见度、可编辑性弱于竞品**。下一步按 A-1 → A-2 → A-3 推进，而不是继续调色。
